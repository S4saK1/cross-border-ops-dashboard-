## 🔍 17 项深度分析总览

### 🔴 CRITICAL（3 项）

#### C1 — Token 存储在 localStorage

| 维度 | 内容 |
|------|------|
| **根因** | `frontend/src/lib/api.ts:5-24` — `localStorage.setItem('token', token)`。PRD 8.1 明确建议 httpOnly Cookie 但未实施。**有意为之但未完成** |
| **影响** | 所有已登录用户。任何 XSS 漏洞即可窃取 24 小时内永久有效的 Token，完全接管账户 |
| **修复方案** | **推荐方案 A**：httpOnly Cookie + SameSite=Strict 迁移（2-3 天）。后端登录端点添加 Set-Cookie 头，前端移除 localStorage 逻辑 |
| **备选方案 B** | BFF + 反向代理全栈改造（2-3 周）。更彻底但 MVP 阶段过重 |
| **依赖** | 无前置依赖，可独立修复 |

#### C2 — Refresh Token 黑名单依赖 SQLite

| 维度 | 内容 |
|------|------|
| **根因** | `backend/app/core/security.py:50-96` — 黑名单使用与业务数据相同的 SQLite。Access Token 完全无法撤销，多实例不同步。**有意为之但未完成** |
| **影响** | 登出后旧 Token 24 小时内仍然有效；多实例部署时黑名单不共享 |
| **修复方案** | **推荐方案 A**：引入 Redis 作为黑名单存储（3-5 天）。TTL 自动过期，多实例共享，`decode_token()` 增加黑名单检查 |
| **备选方案 B** | 迁移 PostgreSQL 后黑名单共存于同一数据库。依赖 C3 完成 |
| **依赖** | 无前置依赖（可选与 C3 合并解决） |

#### C3 — 生产环境 Docker 仍使用 SQLite

| 维度 | 内容 |
|------|------|
| **根因** | `docker-compose.prod.yml:17` — `DATABASE_URL=sqlite:///...`。ADR-001 已存在但未实施。**有意为之但未完成** |
| **影响** | `WORKERS=4` 多 worker 共享单 SQLite 文件，`check_same_thread=False` 绕过线程安全，数据库随时可能损坏 |
| **修复方案** | **推荐方案 A**：按 ADR-001 阶段性迁移至 PostgreSQL（2-3 周）。包括安装驱动、修改连接池、配置 Alembic、数据迁移、修改 compose |
| **备选方案 B** | 临时修复 SQLite 配置 + 计划迁移（2 天）。治标不治本 |
| **依赖** | **强依赖** M5（数据库迁移工具） |

### 🟠 HIGH（4 项）

#### H1 — API 缺少审计日志写入

| 维度 | 内容 |
|------|------|
| **根因** | `api/products.py`、`api/terms.py`、`api/export.py` — CRUD 操作无任何 `AuditLog` 写入。模型和查询 API 已存在但写入逻辑为空。**有意为之但未完成** |
| **影响** | 关键操作零可追溯。PRD 8.3 安全基线未满足。无法回答"谁在何时做了什么" |
| **修复方案** | **推荐方案 A**：装饰器模式 `@audit_log(action="create", resource="product")`（1-2 天），配合 BackgroundTasks 避免阻塞 |
| **备选方案 B** | 数据库触发器 + 领域事件（1-2 周），可扩展性更好 |
| **依赖** | **强依赖** M6（后台任务）— 否则审计写入会显著增加 API 延迟 |

#### H2 — 数据模型缺少外键约束

| 维度 | 内容 |
|------|------|
| **根因** | `models/audit.py:12` — `AuditLog.user_id` 无 `ForeignKey`；`models/term.py:20` — `TermDictionary.created_by` 无 FK。Product 正确设置了 FK，说明属**无心之过** |
| **影响** | 删除用户后审计日志和自定义术语成为孤儿记录，追溯链条断裂 |
| **修复方案** | **推荐方案 A**：添加 FK 定义 + `database.py` 中启用 `PRAGMA foreign_keys=ON`（1 天） |
| **依赖** | **弱依赖** C3（PostgreSQL 原生支持 FK）|

#### H3 — 导出 API 缺少一致性检测阻断

| 维度 | 内容 |
|------|------|
| **根因** | `api/export.py` — `export_csv()` 直接生成 CSV，未调用 `ConsistencyEngine`。PRD 2.3 验收标准明确要求 ERROR 级别阻断。**有意为之但未完成** |
| **影响** | 含术语不一致的 CSV 直接导出上传平台，可能导致 Listing 被拒或降权。核心业务价值（一致性保障）形同虚设 |
| **修复方案** | **推荐方案 A**：在 `export_csv()` 中添加检测拦截（0.5 天）。`ConsistencyEngine` 已实现可直接调用 |
| **备选方案 B** | 实现 PRD 中的 `/export/preview` 双阶段导出（2-3 天） |
| **依赖** | 无前置依赖。`ConsistencyEngine` 可直接使用 |

#### H4 — 分页查询无总页数上限保护

| 维度 | 内容 |
|------|------|
| **根因** | `api/products.py:27`、`api/terms.py:14`、`api/audit.py:14` — `page` 参数仅 `ge=1` 无上限。**无心之过** |
| **影响** | 极端 page 值可遍历所有数据，大偏移量查询在 SQLite 中触发全表扫描（性能 + 安全风险） |
| **修复方案** | **推荐方案 A**：添加 `page` 上限 `le=1000` + 大偏移拦截（0.5 天） |
| **备选方案 B** | 基于游标的分页（3-5 天），需要前端适配 |
| **依赖** | 无前置依赖 |
