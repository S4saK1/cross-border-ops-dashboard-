# ADR-002: 审计日志中间件设计
**状态:** Proposed
**日期:** 2024-01-15

## 背景
当前系统缺少统一的审计日志记录机制，无法追踪用户操作历史。根据技术债评估报告#6，需要补充审计日志写入逻辑，满足合规要求和问题追溯需求。

## 选项分析

### 选项A: 手动在每个API端点添加日志
| 维度 | 评估 |
|------|------|
| 复杂度 | High |
| 成本 | 高 - 需要修改每个API端点 |
| 可扩展性 | 差 - 容易遗漏，维护困难 |

**优点：**
- 可以为每个端点定制日志内容
- 灵活性高

**缺点：**
- 代码重复，维护成本高
- 容易遗漏某些端点
- 无法保证一致性

### 选项B: 使用装饰器模式
| 维度 | 评估 |
|------|------|
| 复杂度 | Medium |
| 成本 | 中 - 需要定义装饰器并应用 |
| 可扩展性 | 中 - 需要手动应用装饰器 |

**优点：**
- 代码复用性好
- 相对集中管理
- 实现相对简单

**缺点：**
- 仍需手动应用到每个端点
- 无法自动覆盖所有端点

### 选项C: 全局中间件
| 维度 | 评估 |
|------|------|
| 复杂度 | Low |
| 成本 | 低 - 一次实现，自动覆盖 |
| 可扩展性 | 优 - 自动处理所有请求 |

**优点：**
- 自动记录所有相关请求
- 无需修改现有代码
- 集中管理，易于维护
- 确保一致性

**缺点：**
- 可能记录过多信息
- 需要过滤不需要记录的请求

## 决策
推荐**选项C: 全局中间件**，理由如下：
1. **实现成本最低**：一次实现，自动覆盖所有端点
2. **维护性最好**：集中管理，易于修改和扩展
3. **一致性最高**：确保所有相关操作都被记录
4. **符合最佳实践**：中间件是FastAPI推荐的日志记录方式

## 具体实现方案

### 中间件设计
1. **请求过滤逻辑**
   - 只记录POST/PUT/DELETE操作（状态修改）
   - 排除GET/HEAD/OPTIONS请求（只读操作）
   - 排除健康检查、监控等端点

2. **日志信息收集**
   ```python
   audit_data = {
       "user_id": get_user_from_token(request),
       "action": request.method,
       "resource_type": extract_resource_type(request.url.path),
       "resource_id": extract_resource_id(request.url.path),
       "details": {
           "path": request.url.path,
           "query_params": dict(request.query_params),
           "body": await request.body() if request.method in ["POST", "PUT"] else None,
           "user_agent": request.headers.get("user-agent"),
       },
       "ip_address": get_client_ip(request),
       "timestamp": datetime.utcnow(),
   }
   ```

3. **存储策略**
   - 异步写入数据库，避免阻塞请求
   - 使用队列机制处理高并发场景
   - 考虑日志轮转和清理策略

### 资源类型提取
```python
def extract_resource_type(path: str) -> str:
    """从URL路径提取资源类型"""
    if "/products" in path:
        return "product"
    elif "/terms" in path:
        return "term"
    elif "/users" in path:
        return "user"
    elif "/auth" in path:
        return "auth"
    else:
        return "unknown"
```

### 用户身份识别
1. **从Token中提取用户ID**
2. **支持匿名操作记录**（如未认证的请求）
3. **处理Token验证失败的情况**

### 性能优化
1. **异步写入**：使用后台任务或队列
2. **批量写入**：累积一定数量后批量插入
3. **索引优化**：为常用查询字段创建索引
4. **日志轮转**：定期清理过期日志

## 影响
### 变容易
- 操作追溯能力显著提升
- 合规性要求得到满足
- 问题排查效率提高

### 变困难
- 增加系统复杂度
- 可能影响请求响应时间
- 需要额外的存储空间

### 需要重新审视的部分
- 数据库性能（审计日志表增长）
- 存储空间规划
- 日志清理策略
- 隐私合规考虑

## 安全考虑
1. **敏感信息脱敏**
   - 密码、Token等敏感字段不记录
   - 请求体中的敏感信息脱敏处理

2. **访问控制**
   - 审计日志访问需要管理员权限
   - 日志导出需要额外权限验证

3. **数据完整性**
   - 日志一旦写入不可修改
   - 实现日志签名机制（可选）

## 测试验证方案
1. **功能测试**
   - 验证POST/PUT/DELETE请求被记录
   - 验证GET请求不被记录
   - 验证用户身份正确识别

2. **性能测试**
   - 并发请求下的日志记录性能
   - 数据库写入性能影响
   - 内存使用情况监控

3. **安全测试**
   - 敏感信息是否被正确脱敏
   - 匿名请求处理
   - 权限控制测试

4. **集成测试**
   - 与现有API的兼容性
   - 错误处理机制
   - 日志查询功能测试
