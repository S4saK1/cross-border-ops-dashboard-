# ADR-001: Access Token短效化 + Redis黑名单
**状态:** Accepted
**日期:** 2024-12-20

## 背景
当前系统存在以下安全和可扩展性问题：
1. **Access Token有效期过长**：24小时有效期，用户登出后旧Token仍然有效
2. **黑名单存储不一致**：Refresh Token黑名单存储在SQLite数据库，多实例部署时不同步
3. **即时吊销能力缺失**：无法在用户登出或管理员撤销权限时立即失效Token
4. **多实例同步问题**：SQLite作为黑名单存储无法支持水平扩展

## 选项分析

### 选项A: 保持现有架构，优化SQLite同步
| 维度 | 评估 |
|------|------|
| 复杂度 | Low - 无需引入新组件 |
| 成本 | 低 - 使用现有SQLite数据库 |
| 可扩展性 | 差 - 无法支持多实例同步 |

### 选项B: 引入Redis作为黑名单存储
| 维度 | 评估 |
|------|------|
| 复杂度 | Medium - 需要引入Redis依赖和连接管理 |
| 成本 | 中等 - 需要Redis实例（开发环境可用Docker） |
| 可扩展性 | 优秀 - 原生支持多实例同步，内存存储性能优异 |

### 选项C: 使用JWT黑名单 + 过期时间
| 维度 | 评估 |
|------|------|
| 复杂度 | Medium - 需要修改Token结构 |
| 成本 | 低 - 无需额外存储 |
| 可扩展性 | 中等 - 依赖Token自包含，但无法支持即时吊销 |

## 决策
选择**选项B: 引入Redis作为黑名单存储**，理由如下：
1. **即时吊销能力**：Redis内存存储支持毫秒级响应，可立即生效
2. **多实例同步**：Redis天然支持分布式部署，所有实例共享同一黑名单
3. **自动过期清理**：Redis支持TTL，可自动清理过期Token
4. **性能优势**：内存存储比SQLite数据库查询快100倍以上
5. **向后兼容性**：可保持现有API接口不变，仅修改内部实现

## 影响

### 变容易的部分
- 用户登出后Token立即失效
- 管理员可以强制撤销用户会话
- 系统可水平扩展支持更多用户
- 开发环境可使用Docker快速启动Redis

### 变困难的部分
- 需要管理Redis连接和配置
- 需要处理Redis故障时的降级策略
- 需要更新部署文档和运维流程

### 需要重新审视的部分
- 现有的SQLite黑名单清理逻辑需要移除
- 单元测试需要更新以支持Redis mock
- 配置管理需要添加Redis相关参数
